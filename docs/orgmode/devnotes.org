* Core architecture: the dispatcher
  :properties:
  :id:       cli-dispatch
  :end:

** The problem
Research pipelines require conflicting environments and a monolithic CLI (e.g., standard ~Typer~ app) fails because importing the top-level module crashes due to conflicting dependencies in sub-modules.

** The solution: dynamic subprocess dispatch
Instead of directly importing modules, ~rgpycrumbs/cli.py~ controls execution flow.
- It scans the directory structure at runtime.
- It runs each script in a subprocess, through ~uv run~ or the active interpreter.
- Each script imports its dependencies in its own process, so one script cannot break another.

#+BEGIN_SRC python
# Logic captured in rgpycrumbs/cli.py
subprocess.run(["uv", "run", "--no-project", "--script", script_path, *args])
#+END_SRC

** Philosophy

The library is designed with the following principles in mind.

- Dispatcher-Based Architecture :: The top-level ~rgpycrumbs.cli~ command is a lightweight dispatcher.
                                   It does not contain the core logic of the tools itself.
                                   Instead, it parses user commands to identify the target script and then runs it in a subprocess.
                                   The dispatcher gives one command-line interface, while the tools stay decoupled.
- Isolated & Reproducible Execution :: Each script is a self-contained unit that declares its own dependencies via PEP 723 metadata.
                                       Under ~uv run~, the ~uv~ runner uses this information to resolve and install the required packages into a cached environment on demand.
                                       This design keeps runs reproducible, and keeps the dependencies of one tool apart from those of another.
- Lightweight Core, On-Demand Dependencies :: The installable ~rgpycrumbs~ package has three core dependencies (~click~, ~numpy~ and ~rich~), and no feature extras.
                                              Under ~uv run~, the dependencies of a command arrive only when the command runs.
                                              Library modules call ~ensure_import~, which can install a missing dependency at first use when ~RGPKGS_AUTO_DEPS=1~ is set, with CUDA-aware resolution.
                                              The base installation stays lightweight either way.
- Modular & Extendable Tooling :: Each utility is an independent script.
                                  This modularity simplifies development and testing, as changes to one tool cannot inadvertently affect another.
                                  New tools can join the collection without changes to the core dispatcher logic, so the system is easy to extend.

* Dynamic dependency resolution
  :properties:
  :id:       dynamic-deps
  :end:

The library extends the PEP 723 dispatcher philosophy to the import surface.
CLI scripts resolve deps via ~uv run~; library modules resolve deps via ~ensure_import~ at first use.
Same principle (lightweight core, on-demand resolution), two execution modes.

** Priority chain

Every call to ~ensure_import(module_name)~ walks a chain of five steps.

1. *Current environment*: ~importlib.import_module()~, with no overhead when the module is installed.
2. *Parent environment*: a fallback to the paths in ~RGPYCRUMBS_PARENT_SITE_PACKAGES~.
3. *uv cache*: a ~sys.path~ lookup in ~$XDG_CACHE_HOME/rgpycrumbs/deps/~.
4. *uv install*: ~uv pip install --target <cache_dir>~, then the import again.
   This step needs ~RGPKGS_AUTO_DEPS=1~ (or the older ~RGPYCRUMBS_AUTO_DEPS=1~), and it skips modules that are not in ~_DEPENDENCY_MAP~.
5. *Fallback*: an ~ImportError~ whose message gives the ~pip install~ line and the ~RGPKGS_AUTO_DEPS~ switch, or points to pixi for ~ira_mod~ and ~tblite~.

** CUDA-aware resolution

The resolver checks whether CUDA is available by probing for ~nvidia-smi~, before it auto-installs a package with GPU backends such as ~jax~.
On CPU-only machines it substitutes CPU-only install specs (e.g. ~jax[cpu]>=0.4~) to avoid pulling hundreds of megabytes of unused CUDA libraries.

** Dependency registry

~_DEPENDENCY_MAP~ in ~rgpycrumbs/_aux.py~ maps importable module names to the pip install specs of their packages, with no feature extras.
This excerpt shows a few of its entries.

#+begin_src python
_DEPENDENCY_MAP = {
    "jax":   "jax>=0.4",
    "scipy": "scipy>=1.11",
    "ase":   "ase>=3.22",
    "chemparseplot": "chemparseplot[neb,plot]>=1.11.0,<2",
    # ... submodules such as "scipy.spatial" map to the same specs
}
#+end_src

Step 4 installs only the packages in this map.
The map leaves out ~ira_mod~ and ~tblite~, which fall through to step 5 with a pixi hint, and heavy packages like ~ovito~, which need an explicit install in the active environment.

** Cache location

The cache directory is ~$XDG_CACHE_HOME/rgpycrumbs/deps/~ (default =~/.cache/rgpycrumbs/deps/=).
~uv~ installs into this directory with ~--target~.
It persists across sessions and can be cleared with ~rm -rf~.

* Library modules
  :properties:
  :id:       library-modules
  :end:

In addition to the CLI dispatcher, ~rgpycrumbs~ provides importable library modules for computational tasks.
These are used by downstream packages like ~chemparseplot~ and can be used directly in notebooks or custom scripts.

** Module structure

- ~rgpycrumbs.surfaces~ :: Surface fitting in ~jax~ with kernel methods: thin plate spline (TPS), Matern 5/2 and inverse multiquadric (IMQ) fits, and gradient-enhanced Matern, IMQ, squared exponential and rational quadratic fits.
                           A Nystrom approximation of the gradient-enhanced IMQ fit handles large data sets.
                           Optional dependency: ~jax~.
- ~rgpycrumbs.geom.analysis~ :: Structure analysis using ASE: distance matrices, bond matrices, and fragment detection via depth-first search on neighbor lists.
                                Optional dependencies: ~ase~, ~scipy~.
- ~rgpycrumbs.geom.ira~ :: Iterative Rotations and Assignments (IRA) for structure comparison by root mean square deviation (RMSD).
                           Optional dependency: ~ira_mod~.
- ~rgpycrumbs.interpolation~ :: Spline interpolation utilities built on SciPy.
                                Optional dependency: ~scipy~.
- ~rgpycrumbs.basetypes~ :: Typed records (dataclasses) for nudged elastic band (NEB) iterations and paths, saddle search measurements, dimer settings, molecular geometries and spin labels.
                            It re-exports them from ~chemparseplot.basetypes~ when ~chemparseplot~ is installed, and otherwise defines local copies, which need only ~numpy~.

** Lazy loading
The top-level ~rgpycrumbs/__init__.py~ uses ~__getattr__~ for lazy imports, so modules with heavy optional dependencies (like ~jax~) are only loaded when accessed.
This keeps ~import rgpycrumbs~ fast regardless of which optional packages are installed.

* Benchmarks
  :properties:
  :id:       benchmarks
  :end:

Performance benchmarks use [[https://asv.readthedocs.io][Airspeed Velocity (ASV)]], and [[https://github.com/HaoZeke/asv-perch][asv-perch]] posts the timing results on pull requests.
The benchmark suite has one file for each computational domain, from surfaces to geometry.

- *Surfaces* (~benchmarks/bench_surfaces.py~) :: Kernel matrix construction in ~jax~, ~GradientMatern~ fit/predict cycles, and prediction-only scaling.
                                                 It warms up the just-in-time (JIT) compiled code in ~setup()~ and calls ~block_until_ready()~ for accurate timing.
- *Interpolation* (~benchmarks/bench_interpolation.py~) :: SciPy B-spline interpolation via ~spline_interp~, parameterized by input size.
- *Geometry* (~benchmarks/bench_geometry.py~) :: ASE ~analyze_structure~ on water clusters, parameterized by molecule count.

** Running locally

The ~bench~ pixi environment has ~jax~, SciPy, ASE and ASV, since it adds the ~surfaces~ and ~test~ features to the ~bench~ feature.

#+begin_src bash
# Validate that all benchmarks parse correctly
pixi run -e bench asv check

# Quick single-pass run (good for smoke testing)
pixi run -e bench asv run \
  -E "existing:$(pixi run -e bench which python)" \
  --quick

# Full run with sample recording
pixi run -e bench asv run \
  -E "existing:$(pixi run -e bench which python)" \
  --record-samples
#+end_src

The ~-E "existing:..."~ flag tells ASV to use the pixi-managed Python rather than building its own virtualenv.
ASV writes the results to ~.asv/results/~, which git ignores.

** CI workflow

Two workflows implement the [[https://asv-perch.rgoswami.me/explanation/fork_security.html][fork-safe split pattern]].

1. ~ci_benchmark.yml~ (=pull_request= trigger, read-only) :: Runs benchmarks for the base and PR commits in a matrix.
                                                             Stashes ~benchmarks/~, ~asv.conf.json~, ~pixi.toml~, and ~pixi.lock~ before each ~git checkout~ so the PR's benchmark code and environment definition apply to both commits.
                                                             Uploads ~.asv/results/~ as artifacts.
2. ~ci_bench_commenter.yml~ (=workflow_run= trigger, write access) :: Downloads the combined artifact and calls ~HaoZeke/asv-perch@v1~ with ~comparison-text-file~ mode to post a formatted table on the PR.

** Writing new benchmarks

Follow the ASV class convention, and mind these points for ~jax~ code.

- Always call ~block_until_ready()~ in the timing body to force synchronous completion of the asynchronous dispatch in ~jax~.
- Warm up the compiled code paths in ~setup()~ with a throwaway call.
  Then set ~warmup_time = 0~, so that ASV does not count the compilation twice.
- Use ~optimize=False~ for surface-fitting benchmarks to measure kernel math rather than the convergence variance of the Broyden-Fletcher-Goldfarb-Shanno (BFGS) optimizer.
